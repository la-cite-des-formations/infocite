1. Vue d'ensemble du système de droits

Le système de droits d'Infocité repose sur un mécanisme personnalisé (non basé sur Spatie ou un package externe) utilisant des flags binaires (bitmask) pour coder les niveaux de permission. Les droits sont gérés via une table polymorphique rightables qui relie :

  • Un droit nommé (enregistrement dans rights, ex : posts, rubrics, comments)
  • Un détenteur (User, Group ou Profil — tous via polymorphisme)
  • Un rôle codé en bitmask (Lecteur, Éditeur, Modérateur, Administrateur)
  • Une ressource cible optionnelle (un article spécifique, une rubrique, etc.)
Principe fondamental : Un utilisateur hérite de droits via trois canaux : ses droits personnels, les droits de ses groupes, et les droits de ses profils. Ces trois sources sont agrégées lors de la résolution.

3. Les rôles binaires

Les rôles sont définis dans la classe app/Models/Roles.php sous forme de constantes binaires :

Constante Valeur binaire Valeur décimale Libellé Signification fonctionnelle (articles)
NONE 0b0000 0 Aucun droit Aucun accès
IS_ADMIN 0b0001 1 Administrateur Suppression d'articles, gestion complète
IS_MODER 0b0010 2 Modérateur Publication / dépublication d'articles, épinglage
IS_EDITR 0b0100 4 Éditeur Création et modification de brouillons
IS_READR 0b1000 8 Lecteur Consultation des articles publiés
ALL 0b1111 15 Tous Combinaison de tous les rôles
Opérations bitmask : La vérification d'un rôle se fait par un AND binaire (&). Par exemple, si un utilisateur a roles = 0b0110 (Éditeur + Modérateur = 6), alors 6 & IS_EDITR (4) donne 4 (truthy) et 6 & IS_ADMIN (1) donne 0 (falsy).

5. Les trois canaux d'attribution des droits

Un utilisateur peut recevoir des droits sur les articles via trois canaux distincts, tous agrégés par la méthode allRights() du trait HasPermissions :

5.1. Canal 1 — Droits personnels

HasPermissions::personalRights()

Droits attribués directement à l'utilisateur dans rightables avec rightable_type = 'User' et rightable_id = user.id.

Exemple : L'utilisateur Jean (id=5) possède le droit posts avec roles = IS_EDITR (4) sur resource_type = 'Rubric', resource_id = 3. → Jean est Éditeur d'articles sur la rubrique 3.

5.2. Canal 2 — Droits hérités des groupes

HasPermissions::groupsRights()

Pour chaque groupe auquel appartient l'utilisateur (table group_user), les droits du groupe (stockés dans rightables avec rightable_type = 'Group') sont agrégés.

Exemple : Le groupe « Communication » possède le droit posts avec roles = IS_EDITR | IS_MODER (6) de façon globale (resource_type = NULL). → Tous les membres de ce groupe sont Éditeurs + Modérateurs sur tous les articles.

5.3. Canal 3 — Droits hérités des profils

HasPermissions::profilesRights() (via allRights())

Un profil est un utilisateur « fictif » (avec name = '@PROFILE') auquel on attribue une configuration de droits standardisée. Les vrais utilisateurs liés à ce profil (table profile_user) héritent de tous ses droits (personnels + groupes) de manière récursive.

Exemple : Le profil « Formateur » possède le droit posts avec roles = IS_READR (8) de façon globale. → Tous les utilisateurs liés à ce profil sont Lecteurs d'articles par défaut.

6. Résolution des droits — méthode hasRole()

app/Models/Traits/HasPermissions.php

6.1. Signature

public function hasRole(
    string $right,           // Nom du droit (ex : 'posts')
    int $role,               // Bitmask du rôle recherché (ex : Roles::IS_EDITR)
    ?string $resource_type,  // Type de ressource ciblée (ex : 'Rubric', 'Post', NULL)
    ?int $resource_id,       // ID de la ressource (ex : 3, NULL)
    bool $extended = TRUE    // Fallback vers le niveau global si non trouvé
): ?int

6.2. Algorithme de résolution

  1. Agrégation : allRights() collecte les droits des 3 canaux (personnels, groupes, profils).
  2. Filtrage : getRightable() filtre par name (droit), resource_type et resource_id, puis trie par priority DESC et retourne le premier résultat.
  3. Test : hasRole() applique l'opération rightable->roles & $role.
  4. Fallback (mode étendu) : Si aucun droit n'est trouvé pour la ressource spécifique et que $extended = TRUE (par défaut), la méthode rappelle hasRole() sans resource_type/resource_id pour chercher un droit global.
Comportement du fallback : Quand $extended = TRUE (valeur par défaut, alias AP::STRICTLY = FALSE), si aucun droit spécifique n'est trouvé sur la ressource précise, le système recherche automatiquement un droit global (sans resource_type/resource_id). Quand $extended = FALSE (passé comme AP::STRICTLY), seul le droit spécifique à la ressource est vérifié et NULL est retourné si non trouvé.

6.3. Retour de hasRole()

Valeur retournéeSignification
int > 0 (truthy)L'utilisateur possède le rôle demandé
0 (falsy)L'utilisateur possède un droit mais pas le rôle demandé
NULLAucun droit trouvé (ni spécifique, ni global en mode étendu)
Subtilité NULL vs 0 : Cette distinction est exploitée par les policies via l'opérateur ?? (null coalescing). Un retour NULL d'un hasRole() strict permet au code appelant de tenter un fallback alternatif.

7. Accès aux rubriques — pré-requis aux articles

Avant toute vérification de droit sur un article, l'utilisateur doit avoir accès à la rubrique contenant l'article. C'est le premier contrôle effectué par chaque méthode de PostPolicy.

7.1. User::myRubrics()

app/Models/User.php — Lignes 299-311

Retourne l'ensemble des rubriques accessibles par l'utilisateur en agrégeant :

  1. Les rubriques de chacun de ses groupes (table group_rubric)
  2. Les rubriques de chacun de ses profils (récursivement via $profile->myRubrics())
public function myRubrics() {
    $myRubrics = new Collection();

    $this->groups->each(function ($group) use (&$myRubrics) {
        $myRubrics = $myRubrics->merge($group->rubrics);
    });

    $this->profiles->each(function ($profile) use (&$myRubrics) {
        $myRubrics = $myRubrics->merge($profile->myRubrics());
    });

    return $myRubrics->unique();
}
Conséquence : Si un utilisateur n'appartient à aucun groupe lié à une rubrique et n'hérite d'aucun profil donnant accès à cette rubrique, il ne pourra jamais accéder aux articles de cette rubrique, même s'il dispose de droits posts globaux.

10. Cas particuliers et subtilités

10.1. Mode strict vs étendu (AP::STRICTLY)

La constante AP::STRICTLY vaut FALSE, ce qui est passé comme valeur de $extended. Quand elle est utilisée, la recherche est restreinte au niveau de ressource spécifié :

// Mode STRICT (AP::STRICTLY = FALSE → $extended = FALSE)
// → Ne vérifie QUE le droit sur la ressource spécifiée
$canCreatePosts = $user->hasRole('posts', IS_EDITR, 'Rubric', $rubricId, AP::STRICTLY);

// Mode ÉTENDU (par défaut, $extended = TRUE)
// → Si pas trouvé sur la ressource → fallback vers le niveau global
$canRead = $user->hasRole('posts', IS_READR, 'Post', $post->id);

10.2. Cascade de vérification (opérateur ??)

Le pattern récurrent dans les policies exploite l'opérateur null coalescing ?? :

// 1. Vérifier STRICTEMENT sur la rubrique enfant
$canCreatePosts = $user->hasRole('posts', IS_EDITR, 'Rubric', $rubricId, AP::STRICTLY);

// 2. Si NULL (aucun droit spécifique trouvé) → fallback sur la rubrique parente
return $canCreatePosts ?? $user->hasRole('posts', IS_EDITR, 'Rubric', $rootRubric->id);

Ce pattern crée une chaîne de résolution à 3 niveaux :

  1. Niveau article/rubrique spécifique (strict)
  2. Niveau rubrique parente (si enfant = NULL)
  3. Niveau global (si parente non trouvé, via le fallback étendu du 2e appel)

10.3. Différence entre article « publié » et « diffusé »

10.4. Droits sur les commentaires

Les commentaires ont leur propre droit (comments) mais sont liés aux articles. La méthode Post::isCommentable() vérifie :

auth()->user()->hasRole('comments', Roles::IS_EDITR, 'Post', $this->id);

Le blocage global des commentaires est géré via Post::allCommentable() qui exclut les articles où le groupe GLOBAL n'a pas le rôle Éditeur sur le droit comments.

10.5. Accès au tableau de bord d'administration

L'accès à la section d'administration des articles est contrôlé par le gate manage-posts défini dans AuthServiceProvider :

Gate::define("manage-posts", function ($user) {
    $right = AP::getModelRight('posts');
    return $user->hasRole($right->name, $right->roles);
});

La valeur de $right->roles provient du champ dashboard_roles de l'enregistrement rights avec name = 'posts'.
